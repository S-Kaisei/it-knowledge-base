# add-topic

対象: $ARGUMENTS

SPEC §7 / §8 / §11 / §12 / §17 / §18 に従う。規約は `.claude/rules/content.md`、詳細は `docs/CONTENT_GUIDE.md`。

## 0. 単一記事かシリーズか判定

- 「体系的に」「基礎から応用まで」など複数記事が必要な場合は、先にシリーズ計画を提示する:
  記事一覧（仮slug・タイトル・カテゴリ・難易度）/ 読む順序 / prerequisites の依存関係 / 既存記事との関係。
- ユーザーが計画を承認したら、各記事について以下 1〜11 を順に実行する。
- 執筆の並列化は、編集ファイルが互いに重ならない場合のみ（双方向リンクの追記は最後にまとめて直列で行う）。

## 手順

1. **テーマと読者の確定**: テーマ、対象読者、カテゴリ、難易度、slug を決める。$ARGUMENTS が曖昧なら妥当な既定値（例: 初学者〜実務1年目、カテゴリは SPEC §6 の主なテーマから推定）を採用し、その旨を明記して進める。本当に判断できない場合のみユーザーに質問する。
2. **重複確認**: `src/content/` を Grep（タイトル・slug・主要語）し、`src/generated/content-index.json` があれば参照する。重複・包含関係があれば新規作成か既存記事の拡充かを判断し報告する。
3. **調査**: `researcher` サブエージェントに委譲する（テーマ、読者、記事の観点、既存記事の slug を渡す）。返ってきた「主張 ↔ 出典 ↔ 確認日」表を保持する。
4. **構成案**: `docs/templates/article.md` を基に見出し構成を作る。不要な見出しは省く。図・シミュレーター・「覚え方」を置く位置（説明のどの段落か）も決める。末尾は「理解度チェック」（自作）と「過去問題」（IPA 過去問、目標 10 問、CONTENT_GUIDE 11 章）。
5. **執筆**: `technical-writer` サブエージェントに委譲する（対象ファイルパス、構成案、調査結果を渡す）か、直接執筆する。新規記事は `draft: true`。
6. **図解**: 説明している段落のすぐ近くに置く。`.claude/skills/create-diagram/SKILL.md` の規約で作成する（Mermaid / SVG / React の選択、ダークモード、代替テキスト、本文での説明）。
7. **記事の接続**: `prerequisites` / `related` を設定し、関連する既存記事側にも双方向に追記する（存在する slug のみ）。
8. **独立レビュー**: `technical-reviewer` サブエージェントを新しいコンテキストで起動し、**記事のファイルパスのみ**を渡す（執筆意図や自己評価は渡さない）。
9. **修正**: blocker / major を修正する。修正後、変更が大きければ 8 を再実行する。全軸4点以上かつ blocker なしを目標とする。
10. **検証**: 実行前に `package.json` の scripts を確認し、無いものは「未整備」と記録する。
    - `docker compose exec web bun run content:check`
    - 反復中: `docker compose run --rm qa bun run verify -- --quick`
    - 最終: `docker compose run --rm qa bun run verify`
    - 図解やレイアウトに影響があれば表示確認する（下書きのまま確認できる）: `docker compose run --rm qa bun run screenshots:drafts -- /<category>/<slug>/`。PNG の目視は `visual-reviewer` に依頼してよい。
    - Docker が使えなければ「未検証」と報告する（成功扱いにしない）。
11. **報告**: 以下の形式で報告する。`draft: false` への切り替えは人間の確認後とする（ユーザーが明示した場合を除く）。

## 最終報告の形式

```text
## 追加した記事
| slug | タイトル | カテゴリ | ファイル | draft |
（変更した既存記事も列挙）
## 調査した情報源
| URL | 確認日 | 用途 | 状態(確認済み/未確認) |
## レビュー結果(5軸)
| 軸 | 点数 | 主な理由 |   ＋ 残った指摘
## 検証コマンドと結果
| コマンド | 結果(成功/失敗/未実行/未整備/未検証) |
## 人間の確認が必要な点
```

## 禁止事項

- 出典・URL の捏造、未確認情報を確認済みとして扱うこと。
- レビュー未実施のまま公開品質と報告すること。
- 実行していない検証を成功と報告すること。
